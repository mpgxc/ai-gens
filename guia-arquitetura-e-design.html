padrões de ARQUITETURA
de software + DDD
+ princípios de CÓDIGO

Padrão de arquitetura não é decoração — é como o sistema vai escalar, falhar e evoluir. Esse guia mapeia 9 padrões essenciais, separa DDD estratégico de DDD tático, mostra como os padrões se misturam em sistemas reais, e fecha com os princípios de código que sustentam qualquer arquitetura no dia a dia. Não decora — consulta quando começar projeto novo ou quando a dor da escolha errada apareceu.

os 4 níveis de decisão arquitetural

Antes dos padrões: entenda os níveis

"Microservices" não é alternativa a "Hexagonal". São níveis diferentes de decisão. Misturar os níveis é a maior causa de discussão estéril em arquitetura. Cada nível abaixo é independente dos outros — você combina um de cada.

Combinação típica em 2026: Modular Monolith (nível 1) + Hexagonal (nível 2) + REST sync com eventos pontuais (nível 3) + DDD tático nos contextos centrais (nível 4). Você ganha clareza arquitetural sem pagar o custo operacional de microservices.

os 9 padrões · descrição · trade-offs · onde aplicar

Detalhe de cada padrão

Cada card tem o nível de decisão (topologia / código / comunicação), a frase-resumo, onde aplicar, quando usar e o trade-off que machuca quando você escolhe errado.

Monolith

clássico
Topologia

"tudo num código só. simples, rápido, gerenciável."

Onde aplicar: backend único, web app inteiro, MVPs, projetos internos, primeiro produto da empresa.

Use: MVP, time pequeno (<10 devs), domínio único.

Deploy 1x, debug fácil, transação ACID grátis. Custa caro depois quando o código vira bola de neve e qualquer mudança puxa tudo junto. Vira o "monolith ruim" quando não há módulos internos.

Modular Monolith

padrão 2026
Topologia

"monólito com fronteiras claras. fatie depois, se precisar."

Onde aplicar: a esmagadora maioria dos backends. Startups passando de MVP, produtos médios, sistemas de gestão.

Use: 90% dos casos.

Bounded contexts no código (cada módulo com seu schema, seus modelos, sua porta pública), mas 1 deploy. Evita complexidade prematura de microservices e mantém a opção de fatiar quando a dor justificar.

Microservices

distribuído
Topologia

"serviços independentes. escala separada, deploy separado."

Onde aplicar: empresas grandes com múltiplos times autônomos, sistemas onde partes diferentes têm escala radicalmente diferente.

Use: > 50 devs, domínios distintos, escala muito assimétrica.

Custa caro em infra e ops. Você troca complexidade de código por complexidade distribuída: rede, observabilidade, transação distribuída, versionamento de contrato e deploy coordenado.

Event-Driven

assíncrono
Comunicação

"serviços conversam por eventos. desacoplados, resilientes."

Onde aplicar: integração entre sistemas legados e novos, fluxos com fan-out (1 evento gera N reações), pipelines de dados, sagas.

Use: integração entre sistemas, fluxos assíncronos, fan-out, audit trail.

Kafka, RabbitMQ, SNS/SQS. Acopla menos, debug é mais difícil. Sem rastreio decente (correlation ID + tracing distribuído) você está cego em produção.

Hexagonal · Ports & Adapters

alistair cockburn
Código

"domínio no centro. infra e UI são plugins intercambiáveis."

Onde aplicar: dentro de cada serviço com domínio rico. Combina perfeitamente com DDD tático e Modular Monolith.

Use: domínio rico, regra de negócio complexa, alta exigência de testabilidade.

Troca DB/framework/queue sem reescrever núcleo. Boilerplate inicial alto — não vale para CRUD puro. Conceito-chave: Port = interface que o domínio declara; Adapter = implementação na borda.

Clean Architecture

uncle bob
Código

"camadas concêntricas. dependência aponta sempre pra dentro."

Onde aplicar: dentro de cada serviço, principalmente em sistemas com regra de negócio explícita e demanda forte por testabilidade. Variante mais formalizada de Hexagonal.

Use: sistemas longa duração, regra de negócio complexa, time grande precisando de regras claras.

4 camadas (Entities → Use Cases → Adapters → Frameworks). Regra única: dependência só aponta pra dentro. Detalhes (DB, web, framework) são plugáveis. Custa muito boilerplate em projeto pequeno.

CQRS

separa leitura
Comunicação

"escrita e leitura têm modelos diferentes. otimiza cada lado."

Onde aplicar: dashboards, relatórios complexos, sistemas de busca, contextos onde a leitura é ordens de magnitude maior que a escrita.

Use: leitura muito diferente da escrita, leitura denormalizada otimizada.

Adiciona complexidade — só com motivo. Eventual consistency é uma realidade que muda como o front pensa o produto. CQS ≠ CQRS: CQS é princípio de método (1 método ou lê ou muda); CQRS é arquitetura (modelos inteiros separados).

Serverless

funções
Topologia

"código por evento. paga por execução, escala sozinho."

Onde aplicar: webhooks, jobs noturnos, ETL, processamento por evento, glue code entre serviços, APIs de baixo tráfego.

Use: tráfego irregular, jobs leves, picos imprevisíveis.

Cold start, processos longos (timeout), lock-in com cloud, observabilidade limitada. Não use para latência crítica em horário de pico baixo nem para fluxos transacionais com muitos passos.

Layered · MVC / Clean

camadas
Código

"camadas conversam só com a vizinha. estrutura familiar a todo dev."

Onde aplicar: CRUD, app web tradicional, dashboards administrativos, sistemas internos. É o default que todo dev junior entende.

Use: CRUD, app web tradicional, time heterogêneo.

Default seguro pra maioria das apps. Vira anêmico fácil — service vira procedural com if-else, repository vira ActiveRecord disfarçado, regra de negócio espalha. Sem disciplina, é praticamente sinônimo de Transaction Script.

hexagonal vs clean architecture · detalhe

Hexagonal × Clean Architecture: irmãs, não gêmeas

Os dois resolvem o mesmo problema (isolar o domínio da infra) com vocabulário diferente. Hexagonal pensa em portas e adaptadores; Clean Architecture pensa em camadas concêntricas com regra de dependência. Você pode entender uma como a versão minimalista da outra.

Quando escolher Hexagonal: projeto começando, time pequeno, foco em testabilidade. Vocabulário enxuto (port + adapter).
Quando escolher Clean Architecture: projeto grande, time heterogêneo, regra precisa ser ensinável. Vocabulário formal (4 camadas, regra de dependência explícita).
Na prática, em código Node.js/TypeScript, os dois costumam acabar parecidos: pasta domain/, pasta application/, pasta infrastructure/.

domain-driven design · estratégico vs tático

DDD: dois lados que poucos separam

DDD é confuso porque o mesmo nome abarca duas coisas muito diferentes. O estratégico resolve "como dividir o sistema" (problema de gente e organização). O tático resolve "como modelar dentro de cada parte" (problema de código). Você pode usar só o estratégico, só o tático, ou os dois — mas precisa saber qual está usando.

DDD Estratégico — desenhar fronteiras

O estratégico fala de Bounded Contexts, Linguagem Ubíqua, Subdomínios (Core/Supporting/Generic) e Context Map. Não é sobre código — é sobre como recortar o problema antes de escrever uma linha. Determina onde os times se separam, quais bases de dados existem, e quais traduções (ACLs) você precisa entre contextos.

DDD Tático — modelar dentro de um contexto

O tático é onde o código mora. Dentro de cada Bounded Context você usa Entities, Value Objects, Aggregates, Repositories, Domain Services e Domain Events. A peça mais importante e mal-entendida é o Aggregate: a fronteira de consistência transacional do seu domínio.

como os padrões se misturam · combinações reais

Combinações que aparecem em sistemas reais

Padrão isolado é abstração. Sistema real é combinação. Aqui estão 3 stacks que cobrem ~95% dos casos backend que você vai encontrar em 2026.

Combo 1

recomendado · 90%

"Modular Monolith + Hexagonal nos módulos Core + DDD tático onde dói + Layered onde não dói."

  • Por que funciona: ganha clareza sem pagar custo de microservices.
  • Custo: baixo. 1 deploy, 1 banco (com schemas separados ou bancos separados por módulo).
  • Quando virar Combo 2: times batendo cabeça em deploy, ou módulos com escala radicalmente diferente.

Combo 2

empresa grande

"Microservices com Hexagonal por dentro + Event-Driven entre eles + Layered nos serviços simples."

  • Por que funciona: times totalmente autônomos, escala independente.
  • Custo: altíssimo. Observabilidade, tracing, contratos versionados, infra de mensageria.
  • Cuidado: não use por modinha. A maioria das empresas chega aqui antes da hora e sofre.

Combo 3

cirúrgico

"CQRS + Event-Driven aplicado APENAS no contexto que precisa, dentro de qualquer um dos combos acima."

  • Por que funciona: isola complexidade onde o trade-off vale.
  • Custo: moderado a alto. Eventual consistency afeta UX.
  • Quando aplicar: dashboards, busca complexa, relatórios. Não no sistema inteiro.
árvore de decisão rápida

Pergunta → Padrão

Quando começar projeto novo, leia da esquerda pra direita. A resposta da direita é o ponto de partida — não o fim.

App novo, time pequeno? → Modular Monolith + Layered
Domínio com regra complexa? → Hexagonal (ou Clean Arch) + DDD tático
Várias equipes, sistema grande? → DDD estratégico antes de qualquer código
Time grande, domínios distintos, deploy independente? → Microservices + Event-Driven
Tráfego irregular, jobs leves, webhooks? → Serverless
Leitura muito diferente da escrita (dashboards, busca)? → CQRS no contexto específico
Integração com sistemas legados/heterogêneos? → Event-Driven + ACL no DDD estratégico
CRUD simples, time heterogêneo? → Layered (MVC) + Modular Monolith
princípios de código · sustentam a arquitetura no dia a dia

Arquitetura escolhe o esqueleto. Princípios escolhem o músculo.

Padrão de arquitetura responde "como o sistema se organiza". Princípios respondem "como cada arquivo, função e classe é escrita". Sem isso, qualquer arquitetura vira spaghetti em 6 meses — Hexagonal, Clean Architecture e DDD são especialmente sensíveis a princípios fracos.

Clean Code

Robert C. Martin

"código se lê muito mais do que se escreve. otimize pra leitura."

  • Nomes intencionais: daysSinceModification > d. Nome ruim é dívida em todo PR.
  • Funções pequenas, uma responsabilidade: se precisa de comentário pra explicar bloco, é uma função nova.
  • Sem flags booleanas: save(user, true) é mistério; saveAndNotify(user) é claro.
  • Comentário é falha de nome: bom código se explica; comentário diz por quê, não o quê.
  • Boy Scout Rule: deixa o arquivo um pouco mais limpo do que encontrou.
// ❌ Ruim
function p(u: User, f: boolean) {
  if (f) send(u.e);
}

// ✅ Bom
function notifyUserByEmail(user: User) {
  sendEmail(user.email);
}

Object Calisthenics

Jeff Bay · 9 regras

"exercícios de OO. force os limites e o código melhora sozinho."

  • 1 nível de indentação por método — força extrair.
  • Não use ELSE — early return, polimorfismo, guard clauses.
  • Encapsule primitives e Strings — Email, CPF, Money são tipos, não string/number.
  • Coleções de primeira classe — OrderList em vez de Order[].
  • 1 dot por linha — Lei de Demeter: a.b().c() revela acoplamento.
  • Não abrevie — customer, não cust.
  • Classes pequenas — máx ~50 linhas, ~5 atributos.
  • Sem getters/setters expostos — Tell, don't Ask.
  • Sem classes com mais de 2 atributos — coesão alta.
// ❌ primitive obsession
function transfer(amount: number, currency: string) { }

// ✅ value object (DDD tático)
class Money {
  constructor(readonly amount: number,
              readonly currency: Currency) {}
  add(other: Money): Money { ... }
}

CQS · Command-Query Separation

Bertrand Meyer

"método ou muda estado, ou retorna valor. nunca os dois."

  • Query (leitura): retorna dado, não muda nada — chamável N vezes sem efeito colateral.
  • Command (escrita): muda estado, retorna void (ou ack/id).
  • Por que importa: previsibilidade. Você lê o nome do método e sabe o que vai acontecer.
  • Em TS/Node: findUserById nunca atualiza last_seen. Crie touchLastSeen separado.
  • CQS ≠ CQRS: CQS é princípio de método; CQRS é arquitetura — separa modelos inteiros.
// ❌ mistura: lê E muda
getUser(id) {
  const u = await repo.find(id);
  u.lastSeen = Date.now();   // 👈 efeito colateral
  await repo.save(u);
  return u;
}

// ✅ separados
getUser(id): Promise<User> { ... }       // query
touchLastSeen(id): Promise<void> { ... } // command

DRY · Don't Repeat Yourself

Hunt & Thomas

"toda regra de negócio mora em UM lugar. duplicação é bug futuro."

  • O que é DRY de verdade: uma regra de negócio num único lugar — não código que parece igual.
  • Cuidado com falso DRY: abstrair antes de saber o padrão é pior que duplicar. "Duplication is far cheaper than the wrong abstraction." — Sandi Metz
  • Regra dos 3: só extraia depois de ver a mesma coisa 3 vezes em contextos parecidos.
  • Não DRY visual: dois cálculos idênticos hoje podem evoluir em direções diferentes amanhã.
  • Foco em conhecimento, não código: "regra de fatura está em 3 lugares" é o problema; "esses 5 forEach parecem iguais" não é.
// ❌ regra repetida em 3 lugares
if (user.age >= 18 && user.country === 'BR') ...

// ✅ regra centralizada (idealmente em VO/Entity)
function canSignContract(user: User): boolean {
  return user.age >= 18 && user.country === 'BR';
}

KISS · Keep It Simple, Stupid

Kelly Johnson

"a solução mais simples que resolve. complexidade só com motivo."

  • Simplicidade > cleverness: código que parece esperto vira pesadelo no plantão.
  • Prefira boring tech: Postgres antes de Cassandra; cron antes de Airflow; monolito antes de microservices.
  • Menos camadas: nem todo projeto precisa de Use Case + Service + Application Service + DTO + Mapper.
  • Otimize por leitura, não escrita: a função que você escreveu em 5 minutos será lida 50 vezes.
  • Métrica prática: se um dev novo não entende o fluxo em 1 hora, está complexo demais.
// ❌ "esperto" demais
const isAdult = (u) => ~~(u.age / 18) > 0;

// ✅ óbvio
const isAdult = (u: User) => u.age >= 18;

YAGNI · You Aren't Gonna Need It

Extreme Programming

"só implementa o que precisa AGORA. o futuro raramente chega como você pensou."

  • Não construa pra "talvez": 80% das abstrações "pro caso de" nunca são usadas e ficam pesando manutenção.
  • Custo escondido: código não-usado tem custo de leitura, teste, documentação, deploy, segurança.
  • Refatore quando a necessidade aparece: é mais barato refatorar com requisito real do que adivinhar.
  • YAGNI não é desculpa pra gambiarra: simples ≠ desleixado. Você ainda escreve código limpo do que existe.
  • Combina com KISS: "não preciso disso" + "se for preciso, faço simples".
// ❌ generaliza pra futuro imaginário
interface PaymentStrategy<T, U, V> {
  process(input: T, opts: U): Promise<V>;
  refund(...): ...;     // nunca chamado
  retry(...): ...;      // nunca chamado
}

// ✅ resolve só o que existe hoje
async function processPayment(order: Order) { ... }
como tudo se encaixa

A pirâmide

Topologia escolhe a forma do sistema. Código escolhe como cada serviço se organiza. Domínio escolhe como você modela o negócio. Princípios mantêm tudo legível. Não dá pra escolher um e ignorar os outros.

🎯

Regra de bolso

Comece Modular Monolith + Layered. Adicione Hexagonal e DDD tático nos contextos com regra complexa. Faça DDD estratégico antes de microservices, nunca depois. Adicione padrões só quando a dor justificar. Arquitetura é trade-off — não troféu. O melhor padrão é o mais simples que resolve seu problema atual + permite o próximo. E lembre: arquitetura sem Clean Code, CQS, DRY, KISS e YAGNI vira ruína em 12 meses, não importa o quão bonita seja no diagrama.
