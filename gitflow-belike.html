GitFlow Simplificado - BuniFlow

Fluxo de branches para desenvolvimento, release e hotfix

⚑ Regras de ouro
  1. 1) master é a fonte da verdade — toda feature/*, hotfix/* e release/* nasce dela.
  2. 2) develop serve apenas para validar em ambiente de testes (QA).
  3. 3) Deploys saem de release/vX.X.X.
  4. 4) Após cada deploy: merge-back em master (com tag) e sync master → develop.
01

Criar uma feature

A feature nasce de master, evolui isolada, é mergeada em develop apenas para validação em QA, e fica aguardando ser incluída em uma release. develop nunca vai para produção.

$ Comandos git — Criar feature
1. Criar a branch
# partir sempre do master atualizado git checkout master && git pull git checkout -b feature/minha-feature
2. Trabalhar e commitar
# commite atômico com mensagem descritiva git add . git commit -m "feat: descrição do que foi feito"
3. Publicar a branch
git push -u origin feature/minha-feature
Bitbucket
PR Abra um Pull Request: feature/minha-feature → develop
Aguarde code review e aprovação antes do merge.
4. Manter branch atualizada com master
# se master evoluiu enquanto você trabalhava git fetch origin git rebase origin/master git push --force-with-lease
5. Após QA aprovado — aguardar release
# feature fica viva, será incluída em uma release/vX.X.X # NÃO mergear diretamente em master
02

Criar release & fazer deploy

Quando há N features aprovadas em QA, cria-se uma release/vX.X.X a partir de master, agregam-se as features, faz-se o deploy e depois sempre merge-back em master (com tag) + sync em develop.

$ Comandos git — Criar release & deploy
1. Criar a release a partir de master
git checkout master && git pull git checkout -b release/v1.2.0 git push -u origin release/v1.2.0
2. Agregar features aprovadas via PR
Bitbucket
PR Para cada feature aprovada em QA, abra um Pull Request:
feature/A → release/v1.2.0  |  feature/B → release/v1.2.0
Repita para cada feature que entrará nesta release.
3. Deploy disparado pelo CI/CD
# CI/CD detecta a branch release/* e deploya automaticamente # ou dispare manualmente conforme pipeline do time
4. Após deploy OK — tag local e push
# a tag marca o ponto exato que foi para produção git checkout release/v1.2.0 && git pull git tag -a v1.2.0 -m "Release 1.2.0" git push origin v1.2.0
5. Merge-back release → master via PR
Bitbucket
PR Abra Pull Request: release/v1.2.0 → master
Somente após aprovação o merge é executado.
6. Sync master → develop via PR
PR Abra Pull Request: master → develop
Mantém o ambiente de QA atualizado com o que foi para produção.
7. Limpar branches locais
git branch -d release/v1.2.0 feature/A feature/B git push origin --delete release/v1.2.0 feature/A feature/B
03

Resolver conflitos

Há dois cenários comuns, cada um com sua estratégia. Identifique primeiro de onde vem o conflito — se de master (feature ficou atrás) ou de develop (outra feature em QA tocou o mesmo código).

▸ git diff origin/master...feature/xyz vs. git diff origin/develop...feature/xyz → onde aparecem os conflitos?
SE o conflito vem de master
→ outro dev mergeou algo antes de você
→ use Cenário A (rebase)
SE o conflito vem só de develop
→ outra feature em QA tocou o mesmo código
→ use Cenário B (branch de resolução)
❌ O que nunca fazer na resolução de conflitos
❌ Resolver conflitos pela interface web do Bitbucket (ou GitHub/GitLab)
A interface web cria merge commits automáticos sem mostrar o contexto completo do conflito. Você tende a aceitar versões incorretas sem perceber, o diff fica confuso, não há como testar o resultado antes de commitar, e o histórico fica poluído com resoluções incompletas. Sempre resolva localmente, teste, e só então suba.
❌ Mergear develop dentro da sua feature/*
Isso contamina a sua feature com código de outras features que ainda estão em QA — e que talvez não entrem na mesma release. Cria dependências invisíveis: sua feature passa a precisar de código que não veio de master. Quando a release for composta, haverá commits estranhos na sua branch. Use o Cenário A (rebase) ou o Cenário B (conflict branch), nunca git merge develop dentro de uma feature.
❌ Usar git push --force (sem --lease)
O --force simples sobrescreve cegamente o remote, podendo destruir commits que outro dev pushnou enquanto você rebbaseava. O --force-with-lease verifica se o remote não avançou desde seu último fetch e aborta se avançou. Sempre use --force-with-lease. Nunca use --force em branches compartilhadas.
❌ Fazer git rebase em branches compartilhadas (develop, release/*, master)
Rebase reescreve o histórico. Em branches que outras pessoas usam, isso cria estados divergentes impossíveis de reconciliar sem force-push destrutivo. Rebase é permitido somente em feature/* e hotfix/* que são suas.
A

Conflito com master — feature desatualizada

Outro time mergeou em master enquanto você estava na feature. Estratégia: rebase da feature contra master, resolver, push --force-with-lease. A feature continua sendo a branch de trabalho.

$ Comandos git — Cenário A: rebase contra master
1. Atualizar referências remotas
git fetch origin
2. Rebasear a feature no topo de master
git checkout feature/xyz git rebase origin/master
3. Se houver conflito durante o rebase
# edite os arquivos conflitantes, depois: git add . git rebase --continue # repita para cada commit conflitante
4. Abortar o rebase (se quiser recomeçar)
git rebase --abort
5. Force-push seguro na feature
# --force-with-lease aborta se alguém pushnou antes de você git push --force-with-lease origin feature/xyz
6. Re-abrir / atualizar PR → develop para QA
Bitbucket
PR O PR existente de feature/xyz → develop já foi atualizado pelo force-push.
Solicite novo review se necessário e aguarde aprovação para o merge.
B

Conflito com develop — outras features em QA tocaram o mesmo código

O conflito não vem de master (rebase não resolve) — vem de outra feature já em develop. Estratégia: criar uma conflict/* a partir de develop, mergear a feature lá, resolver e abrir PR. A feature original fica intacta para entrar na release depois.

$ Comandos git — Cenário B: branch de resolução de conflito
1. Atualizar develop local
git checkout develop && git pull
2. Criar branch de resolução a partir de develop
# prefixo conflict/ deixa claro a natureza da branch git checkout -b conflict/feature-xyz-to-develop
3. Mergear a feature na branch de resolução
git merge feature/xyz # aqui o conflito aparecerá localmente — é seguro, é uma branch sua
4. Resolver os conflitos e commitar
# edite os arquivos conflitantes, depois: git add . git commit
5. Publicar a branch de resolução
git push -u origin conflict/feature-xyz-to-develop
6. Abrir PR → develop
Bitbucket
PR Abra Pull Request: conflict/feature-xyz-to-develop → develop
O revisor consegue ver exatamente como o conflito foi resolvido.
7. Limpar a conflict branch após merge
git branch -d conflict/feature-xyz-to-develop git push origin --delete conflict/feature-xyz-to-develop
✅ feature/xyz continua intacta para a release
# quando chegar a hora, a feature entra na release via PR normalmente
04

Hotfix (correção urgente em produção)

Hotfix nasce de master (mesma regra das features), valida rápido em develop, gera uma release/vX.X.1 patch, deploya, merge-back + tag, sync final.

$ Comandos git — Hotfix completo
1. Criar hotfix a partir de master
git checkout master && git pull git checkout -b hotfix/bug-critico
2. Corrigir, commitar e publicar
git add . git commit -m "fix: corrige bug crítico X em produção" git push -u origin hotfix/bug-critico
3. Validar em develop (QA rápido) via PR
Bitbucket
PR Abra Pull Request: hotfix/bug-critico → develop
Review rápido e merge para validar o fix no ambiente de QA.
4. Criar release patch a partir de master
git checkout master && git pull git checkout -b release/v1.2.1 git push -u origin release/v1.2.1
5. Agregar o hotfix na release via PR
PR Abra Pull Request: hotfix/bug-critico → release/v1.2.1
Aprovado → merge → CI/CD deploya.
6. Tag local após deploy OK
git checkout release/v1.2.1 && git pull git tag -a v1.2.1 -m "Hotfix 1.2.1 — corrige bug X" git push origin v1.2.1
7. Merge-back release → master via PR
Bitbucket
PR Abra Pull Request: release/v1.2.1 → master
8. Sync master → develop via PR
PR Abra Pull Request: master → develop
Garante que o fix de produção chegue ao ambiente de QA.
9. Limpar branches
git branch -d hotfix/bug-critico release/v1.2.1 git push origin --delete hotfix/bug-critico release/v1.2.1

Regras de ouro

  • • master é fonte da verdade — protegida, só merge via PR
  • • feature/* e hotfix/* sempre nascem de master
  • • develop é ambiente de QA, nunca alvo de deploy
  • • Deploy sai de release/vX.X.X, nunca de develop
  • • Após deploy: merge-back em master com tag + sync master → develop
  • • Nunca force-push em master, develop ou release/*

Comandos essenciais

  • • git checkout -b feature/xyz master
  • • git fetch origin && git rebase origin/master
  • • git push --force-with-lease (só em feature/*)
  • • git checkout -b conflict/feat-xyz-to-develop develop
  • • git merge feature/xyz (na conflict branch)
  • • git checkout -b release/v1.2.0 master
  • • git merge --no-ff feature/xyz
  • • git tag -a v1.2.0 -m "Release 1.2.0"
  • • git push origin v1.2.0

Checklist pós-deploy

  • ☐ Deploy validado em produção (smoke tests)
  • ☐ release/vX.X.X mergeada em master (--no-ff)
  • ☐ Tag vX.X.X criada e pushada
  • ☐ master sincronizada em develop
  • ☐ Branches feature/* incluídas na release foram deletadas
  • ☐ Release notes publicadas
  • ☐ release/vX.X.X deletada (a tag preserva o histórico)
